## 4. Subsystem purposes

**`FilterUtils/`** (`FilterUtils.py`, `__init__.py`) — Image-filter selection logic used before any intervention is dispatched. `get_image_filter_information()` (`FilterUtils.py:53`) sends the image plus the user's filter texts to OpenAI's `gpt-4o` (hardcoded at `FilterUtils.py:165`) using structured `beta.chat.completions.parse` with Pydantic response models (`ImageFilterAnalysis`, `FilterElementAnalysis`), asking it to score each candidate filter element's presence/coverage/centrality and (optionally) recommend up to 5 interventions from a hardcoded `AVAILABLE_INTERVENTIONS` list (`FilterUtils.py:21-27`) with human-readable descriptions baked into the prompt (`FilterUtils.py:62-127`). `get_best_filter()` (`FilterUtils.py:197`) picks the single best-matching filter object via a weighted `0.4*coverage + 0.6*centrality` score (`FilterUtils.py:231`) and returns a `FilterResult` with `top3_interventions`/`next2_interventions` split out for the ranking workflow.

**`ImageProcessor/`** (`ImageProcessor.py`, `ObjectDetector/GroundingDINODetector.py`, `ObjectDetector/ObjectDetector.py`) — The entry point called synchronously from `processors/base_processor.py` for every post image. `ImageProcessor.process_image()` (`ImageProcessor.py:32`) calls `FilterUtils.get_best_filter` to decide which filter/interventions apply, then builds a JSON payload and enqueues `tasks.run_intervention_workflow.delay(...)` (lines 92, 115) rather than blocking, returning a `"status": "DEFERRED"` dict immediately. `ObjectDetector/GroundingDINODetector.py` wraps HuggingFace's `AutoModelForZeroShotObjectDetection`/`AutoProcessor.from_pretrained(...)` (lines 12,19,23,27) for local, API-key-free bounding-box detection — an alternative to the OpenAI/Gemini VLM path, registered in `tasks.py`'s `MODEL_REGISTRY` as `"local"`/`"grounding_dino"`.

**`interventions/`** (`base.py` + one file per intervention: `blur.py`, `inpainting.py`, `occlusion.py`, `replacement.py`, `shrink.py`, `stylization.py`, `warning.py`, and the deterministic-style family `stylize_cubism.py`/`stylize_impressionism.py`/`stylize_ghibli.py`/`stylize_pointillism.py` plus their `selective_stylize_*.py`/`selectivestylization.py` region-limited counterparts) — Each file defines a class extending `interventions/base.py:ImageIntervention` with an `.apply(image_bytes, filters, model)` method; these are the pluggable implementations registered by name in `tasks.py:INTERVENTION_REGISTRY` (`tasks.py:60-77`) and invoked by the Celery batch/direct tasks.

**`llm/`** — All LLM-driven text/filter logic. `processor.py` (720 lines) holds `LLMProcessor` (content-match evaluation + marker-based text intervention) and `ContentFilter`/`FilterMatch` data classes; `chat.py` holds `FilterCreationChat` (conversational filter creation, backs `/chat` and the WS `chat` message type); `vision.py` holds `VisionFilterCreator` (image-based filter creation, backs `/chat/image`); `filter_creator.py` holds `FilterCreator` (one-shot NL→filter conversion); `prompts.py` centralizes prompt text (filter creation/evaluation prompts, image-scorer prompts); `chat_system_prompt.py` holds the system prompt for the conversational flow; `response_models.py` defines Pydantic response schemas (e.g. `TextInterventionEvaluation`) for structured LLM output. `llm/__init__.py` re-exports `LLMProcessor, ContentFilter, FilterMatch, FilterCreator, FilterCreationChat, VisionFilterCreator, prompts, chat_system_prompt`.

**`ml_models/`** (`base.py`, `openai_models.py`, `gemini_models.py`, `grounding_dino_model.py`) — Provider-pluggable model wrappers used by the Celery image-intervention pipeline, each implementing a common interface (`base.py:ImageModel`) with methods like `describe_image`, `generate_from_prompt`, `edit_image`, `score_image`/`score_image_two_stage`, `detect_objects`. Registered in `tasks.py:MODEL_REGISTRY` as `"openai"`, `"gemini"`, `"local"`/`"grounding_dino"` (`tasks.py:80-85`).

**`processors/`** — Platform dispatch + shared pipeline. `base_processor.py` defines `Post` (platform-agnostic post wrapper with `[TITLE]`/`[BODY]` marker handling) and `ContentProcessor` (loads filters from the DB, runs `LLMProcessor.evaluate_content`/`process_content`, and for each post image calls `ImageProcessor.process_image`); `reddit_processor.py`/`twitter_processor.py` subclass it for platform-specific HTML/JSON parsing (dispatched from `app.py:177-180`'s `PLATFORM_PROCESSORS` map); `standalone_custom_processor.py` (579 lines) implements the isolated `/custom-feed/*` and custom-feed WS pipeline (`StandaloneCustomProcessor`, `process_custom_feed_request`, `process_auto_filter_request`) used for research/comparison feeds, independent of the live extension flow.

**`ServerCache/`** (`Cache.py`, `RedisCache.py`, `CacheManager.py`, `Singletons.py`) — Caches processed-image results so repeated image+filter combinations don't re-trigger the expensive Celery pipeline. `Cache.py` is an abstract interface; `RedisCache.py` is the concrete Redis-backed implementation; `CacheManager.py:ImageCacheManager` (184 lines) builds cache keys from `image_url + sorted filter strings` (`CacheManager.py:71-72`), and on a cache miss for the exact filter string, asks an LLM (Gemini `gemini-2.5-flash` via OpenAI-compatible endpoint, `CacheManager.py:21-22`) to find the closest existing filter key as a fuzzy-match fallback; on `set_processed_value_to_cache` it also publishes to the Redis pub/sub channel `image_processing_complete` (`CacheManager.py:164`) and/or calls a registered `websocket_callback`. `Singletons.py` exposes the single process-wide `image_cache = ImageCacheManager()` instance imported everywhere else (`ServerCache/__init__.py`).

**`custom_feed_models_pkg/`** (`custom_feed_models.py`, 151 lines) — Pydantic request/response models exclusively for the custom-feed research path: `CustomFeedPost`, `CustomFeedRequest`, `ProcessedPost`, `CustomFeedResponse`, plus `PostPreference`/`HumanPreferenceSubmission`/`HumanPreferenceResponse`-style models for the `/human-preferences/*` endpoints. Explicitly documented in its own docstring (lines 1-5) as isolated from the main browser-extension models.

**`utils/`** — Cross-cutting helpers. `config.py` (`ConfigManager`, 161 lines) is the singleton YAML+env config loader described in CLAUDE.md, with Pydantic sub-configs (`LLMConfig`, `ProcessingConfig`, `DatabaseConfig`, `LoggingConfig`, `TestingConfig`, `ExternalServicesConfig`) and `_apply_env_vars()` (`config.py:111-129`) mapping `OPENAI_API_KEY`/`CONTENT_PROCESS_MODEL`/`FILTER_CREATION_MODEL`/`CHAT_MODEL`/`DEBUG_MODE`/`PROCESSING_MODE`/`PARALLEL_WORKERS` env vars onto config fields; `storage.py` (`_StorageManager`, 85 lines) picks between S3 (`boto3`) and local-disk (`temp/uploads/`) storage based on the `USE_S3` env var (`storage.py:23`), defaulting to `True` in code but the git-status note says it's currently run with `USE_S3=false`/local; `errors.py` defines custom exceptions (`LLMError`, `ProcessorError`) and `handle_processing_errors`/`handle_api_errors` decorators; `logging.py` wires up `setup_logging()` (used in `app.py:47`); `default_filters.py` supplies the test/default filter seed data referenced by `database/operations.py:82`; `preference_manager.py` (`PreferenceManager`) resolves a user's processing mode/intensity preferences, used in `base_processor.py:76`; `json_utils.py` holds small JSON helpers.

### `Backend/ml_models/`

`find ml_models -type f -size +500k` returned **no results** — there are no large binary/weight files checked into this directory. This matches the code-level finding (Section 5) that the GroundingDINO model is loaded at runtime via `AutoModelForZeroShotObjectDetection.from_pretrained(...)` (HuggingFace Hub download/cache), not from a committed weights file. No `.pt`/`.pth`/`.onnx`/`.bin`/`.safetensors` files were skipped because none exist in this directory.
